# API Routes

Blade is designed so that you never need to write a REST API for your own frontend. Reading data happens through the `use` hook in server components, and writing data happens through `useMutation` in client components. All server communication is channeled through mutations — there is no fetch call, no endpoint to write.

The only reason to expose a REST API is if you need to serve a third-party client: a mobile app, a partner integration, or a script that cannot use Blade's query syntax.

## Auto-Generated REST API

For those cases, Blade automatically generates a REST API at the `/api` URL path. It exposes your Triggers through an auto-generated request schema. You enable it per-model in your schema definition — no hand-written controllers needed.

## Custom API Routes

In the rare case that you need a specific request signature, add a `router.ts` file at the root of your project and export a [Hono](https://hono.dev) app:

```typescript
import { Hono } from 'hono';

const app = new Hono()
  .post('/some-path', (c) => c.text('Testing'));

export default app;
```

Blade mounts this Hono app alongside your Blade app on the same domain. The two apps are independent — the Hono routes cannot reach into Blade's data layer.

> **Note:** Prefer Blade's auto-generated REST API over custom routes whenever possible. Custom routes are an escape hatch for edge cases where the trigger-based approach doesn't fit.
